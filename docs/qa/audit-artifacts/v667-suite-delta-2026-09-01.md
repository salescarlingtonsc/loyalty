# Executed-suite delta after repairing the migration chain

Measured 2026-09-01 against `origin/main` @ `3414eb78`.

| Run | Failures |
|---|---:|
| A. `origin/main`, unmodified | **7** (+ the v599 migration failure itself) |
| B. harness fix applied, **without** v667 | **22** |
| C. harness fix + v667 (fix and its regression test) | **22** |

**B == C, so v667 introduces zero regressions.** The 15-failure increase between A and B is
caused by the chain now actually applying v600–v665. Those tests were green only because the
harness stopped at v599 and never reached the migrations that changed the behaviour they assert.

`v422_baseline_behaviours.sql` is the file the harness's own header designates the **regression
floor** — the one test that "must pass in BOTH" phases. It does not.

## Probable dominant cause: the v625 platform-session rule

`app.is_super_admin()` was rewritten by `nestly_v625_platform_google_only` to require a Google
SSO session, not merely a `super_admins` row:

```sql
select exists (select 1 from public.super_admins sa where sa.user_id = auth.uid())
   and app.platform_session_via_google_v625();
```

and that predicate demands `amr[0].method = 'oauth'` plus `app_metadata.providers` containing
`'google'`.

Every newly-failing test that impersonates a user sets a bare claim set and supplies **none** of
those claims:

| Test | `request.jwt.claim*` calls | `amr` / google claims |
|---|---:|---:|
| v510_operating_system_crm_foundation | 24 | **0** |
| v512_commercial_handoff_integrity | 16 | **0** |
| v513_onboarding_next_actor_and_review | 7 | **0** |
| v555_business_pot_fails_closed | 2 | **0** |
| v422_baseline_behaviours | 1 | **0** |

which matches the observed errors (`prospecting_access_required`, `customer read access
required`). This is the same trap the v667 fixture hit: a bare `sub` claim is refused by design,
so a test written before v625 now fails for a fixture reason rather than a product reason.

`v552_gated_evidence_isolation` sets no claims at all and is likely a separate cause; it has not
been diagnosed here.

## Why this matters more than the count

Two of these are not "flaky tests":

1. **The regression floor is red.** The harness's contract is that v422 passing in both phases is
   what makes it a floor rather than a description of whatever shipped last. That contract is
   currently unmet.
2. **Green meant nothing here.** Before the chain was repaired, the suite reported *"all executed
   SQL passed"* while 15 of its own tests would have failed against the real schema. A truncated
   chain does not fail loudly — it silently narrows what is under test.

## Recommended handling

These are **not** in v667's scope and were deliberately left failing rather than patched, so the
delta stays legible to a reviewer. Each needs triage into one of:

- **fixture-only** — add the v625 platform-session claims and re-run (expected majority);
- **real regression** — a v6xx migration changed behaviour an older test correctly protects, in
  which case the migration is the defect, not the test.

That triage must not be done by the same pass that repaired the chain: a fixture edit that makes
a red test green is indistinguishable from concealing a regression unless the two are judged
separately.
